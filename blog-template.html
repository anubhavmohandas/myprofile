How an LLM patches its own dependencies.

Most tools tell you a CVE exists. SAGE finds the function, writes the fix, proves the fix, opens the PR — and waits for you to wake up.

In December 2021, the world learned that log4j — a library most developers had never typed but every JVM service in production imported — had been a remote code execution time bomb for years. Dependabot saw the CVE. It opened tickets. Nobody knew which functions were actually affected. The patching happened by exhausted humans, manually, over weeks.

I built SAGE because I wanted to know: can an LLM do this part of the work? Not the "is there a CVE" part — that's solved. The actual read-the-code, locate-the-vulnerability, write-the-patch, prove-the-patch part. The part that used to require a human.

The naive version is wrong

You might think: pull the CVE, paste the affected file into Claude, ask for a fix, open a PR. I tried that. It produced patches that compiled and looked right and broke things silently. The model was confident; the model was wrong; the human reviewing the PR couldn't tell because everything looked plausible.

Three problems sat on top of each other:

  • Wrong scope. The vulnerability was in a function the LLM didn't see, called transitively five hops away.
  • Wrong context. The patch broke a downstream caller because the LLM didn't know who called this function.
  • No proof. "It compiles" is not "it's fixed." Nobody had asked: does the exploit still work against this version?

Synapse: the graph that makes the LLM honest

Before SAGE sends anything to Claude, it builds a code knowledge graph called Synapse. tree-sitter parses every function in the codebase. NetworkX stores the call relationships as a directed graph. When a CVE lands, SAGE queries the graph:

"Find every function in this codebase that — directly or transitively — calls into the vulnerable library function. Bound the search at depth 6. Return the union as the blast radius."

Only those functions reach the LLM. Everything else stays out of the prompt. The model sees a small, precise universe instead of a vague codebase. Token budgets stop being a wall.

Semgrep before the LLM

The LLM is not the first reader. Semgrep is. SAGE runs structural pattern detection first — patterns for SQL injection, command injection, XSS, deserialization gadgets. Semgrep doesn't speculate. If it finds a structural match, the vulnerability is real. 

# a Semgrep rule SAGE uses for command injection
rules:
  - id: subprocess-shell-true
    pattern: subprocess.$FN(..., shell=True, ...)
    severity: ERROR
    message: shell=True with user input is RCE

Now the LLM gets called with: here's the function, here's the Semgrep finding, here's the CVE description, generate a patch that addresses all three. The hypothesis space is small. The prompt is bounded. The output is testable.

The test before the fix

Before SAGE writes the patch, it writes the test that would catch the patch failing. The test is CVE-specific: it constructs the exact attack payload from the advisory and runs it against the un-patched function to confirm the test fails. Then SAGE writes the patch, re-runs the test, and confirms it passes. If anything else in the existing test suite goes red, the patch is rejected.

Most patch-generation pipelines I've seen run tests after the LLM is done. SAGE runs them before, during, and after. The test is the spec; the patch is the answer.

What I changed my mind about

I started this project believing the LLM would do the heavy lifting. After three months of building it, I think the LLM is the smallest component. The graph is the work. The static analysis is the work. The test generation is the work. The model writes 30 lines of diff at the end of a long, expensive pipeline whose job is to make those 30 lines obvious.

That is how I think autonomous systems should be built in general. Most of the engineering is in narrowing the question until the model has nothing left to invent.

SAGE is in active development. PRs to the design — not the code, the design — are welcome at github.com/anubhavmohandas.
